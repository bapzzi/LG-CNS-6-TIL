# <LG CNS 6기] 28일차 TIL — 자바 — 1:N 조회·Optional 예외·객체 복사

> TL;DR: 블로그 상세 화면이 보던 서버를 흉내용에서 직접 만든 것으로 옮겼다. 글 하나에 댓글 여럿이 딸린 관계를 서버가 조립해 한 번에 돌려준다. 조회해 온 객체를 그 자리에서 고치는 형태는 권장되지 않는 것으로 표시돼 있고, 복사해서 새로 만드는 형태가 쓰인다.

## 🗺️ 한눈에 보기

### 오늘은 무엇을 위한 작업이었나

블로그 글 하나를 열면 **글 본문과 그 글에 달린 댓글이 같이** 보여야 한다. 댓글을 새로 쓰면 목록 맨 아래에 바로 붙어야 한다. 이 화면 한 벌을 직접 만든 서버로 옮겨 붙이는 것이 하루의 도착점이다.

```
[화면] 글 상세 열기
   │  GET /blogs/read/{id}   Authorization 헤더에 토큰
   ▼
[서버] 글 1건 조회 ──┐
                    ├─→ 하나로 합쳐서 돌려준다
      댓글 N건 조회 ─┘      { id, title, content, comments: [ ... ] }
   │
   ▼
[화면] 본문 + 댓글 목록 렌더

[화면] 댓글 작성
   │  POST /comments/insert
   ▼
[서버] 시퀀스에서 id를 먼저 받아 저장 → 그 id를 응답에 실어 보냄
   │
   ▼
[화면] 목록 배열 끝에 새 댓글만 덧붙임 (전체 재조회 없음)
```

### 무엇이 무엇을 불러왔나

화면 네 갈래가 서버로 옮겨졌다. 목록·글쓰기·상세·댓글 등록이다. 이 중 뒤의 둘이 서버 쪽 구조를 끌고 왔다.

```
글 상세를 한 번에 보여주려면
   → 응답 DTO가 댓글 배열을 품어야 한다        (1:N)
   → 없는 번호가 들어올 수 있다                 (Optional · 예외)
   → 조회 결과에 댓글을 채워 넣어야 한다        (복사 후 새 객체)

댓글을 쓰고 목록에 바로 붙이려면
   → 저장하면서 만들어진 번호를 알아야 한다     (시퀀스 · selectKey)
   → 그 번호를 응답에 실어 보내야 한다          (201 + 본문)
```

앞자리에 이론이 하나 붙는다. 로그인 상태를 유지하는 방식이 세션에서 토큰으로 넘어간 이유다.

## 🧭 오늘의 학습 키워드

| 키워드 | 한 줄 정리 | 오늘 어디에 쓰였나 |
|---|---|---|
| 세션 | 서버가 접속자 상태를 기억해 두는 방식 | 토큰으로 바꾼 이유의 출발점 |
| JWT | 상태를 접속자가 들고 다니는 토큰 | `Authorization` 헤더로 전달 |
| 게이트웨이 | 여러 서비스 앞에 서는 단일 관문 | 세션이 서비스 간에 공유되지 않는 자리 |
| 시퀀스 | 번호를 순서대로 발급하는 DB 객체 | `BLOG_SEQ` · `COMMENT_SEQ` |
| NEXTVAL | 시퀀스에서 다음 번호를 꺼낸다 | INSERT의 ID 자리 |
| selectKey | INSERT와 별도로 키 값을 조회하는 태그 | 댓글 id를 미리 받아 온다 |
| order="BEFORE" | INSERT보다 먼저 실행하라는 지정 | 시퀀스 방식에서 쓴다 |
| Optional | 값이 없을 수 있음을 타입으로 표시 | `findById`의 반환 타입 |
| orElseThrow | 값이 없으면 예외를 던진다 | 없는 글을 요청했을 때 |
| @PathVariable | 주소 경로의 일부를 값으로 받는다 | `/blogs/read/{id}` |
| @RequestHeader | 요청 헤더 값을 받는다 | `Authorization` |
| 1:N | 한 건에 여러 건이 딸린 관계 | 블로그 1 : 댓글 N |
| toBuilder | 기존 객체를 복사해 일부만 바꿔 새로 만든다 | 댓글을 채운 응답 객체 |
| @Transactional(readOnly) | 이 작업은 읽기만 한다는 표시 | 목록·상세 조회 메서드 |
| 204 NO_CONTENT | 성공했으나 돌려줄 본문이 없다 | 목록이 비었을 때의 선택지 |

## ✍️ 공부한 내용

### 1. 세션에서 토큰으로

웹은 요청 하나가 끝나면 서버가 그 사람을 잊는다. 로그인한 사람인지 계속 알아보려면 어딘가에 표시를 남겨야 한다. 그 표시를 **서버가 보관하면 세션**, **접속자가 들고 다니면 토큰**이다.

바꾸는 이유는 서비스를 여러 개로 쪼갤 때 드러난다. 세션은 그것을 만든 서비스 안에만 있다. 주문 서비스에서 로그인했는데 결제 서비스로 넘어가면 그쪽은 이 사람이 누구인지 모른다. 토큰은 요청에 실려 다니므로 **앞단 관문(게이트웨이)에서 한 번 확인하면 뒤쪽 서비스들이 그대로 쓴다.**

> 💡 세션은 서비스 경계를 못 넘고, 토큰은 요청을 따라다녀서 넘는다.

싣는 자리도 정해져 있다. 토큰은 본문이 아니라 **헤더**에 넣는다. 본문은 다루려는 데이터가 들어가는 칸이고, 토큰은 데이터가 아니라 신원 표시다.

```java
@GetMapping("/read/{id}")
public ResponseEntity<?> read(  @PathVariable("id") Integer id,
                                @RequestHeader("Authorization") String at) {
```

- `@PathVariable`은 주소 경로 안의 값을, `@RequestHeader`는 헤더 값을 각각 받는다.
- 27일차에 헤더로 내보낸 토큰이 이번에는 헤더로 들어오는 자리다.

대가도 같이 온다. 토큰은 한 번 발급되면 만료 전까지 유효하다. 서버가 보관하지 않으니 **중간에 회수하기 어렵다.** 세션은 서버가 지우면 그 즉시 끝난다.

### 2. id를 시퀀스에서 받아 오기

글과 댓글은 저장하는 모양이 다르다. 같은 시퀀스를 쓰는데 꺼내는 시점이 다르다.

글은 INSERT 문 안에서 번호를 바로 뽑는다.

```xml
<insert id="save" parameterType="...BlogRequestDTO">
    INSERT INTO SPRING_BLOG_TBL(ID, TITLE, CONTENT, CATEGORY, EMAIL)
    VALUES(NEXTVAL(BLOG_SEQ), #{title}, #{content}, #{category}, #{email})
</insert>
```

- `NEXTVAL(BLOG_SEQ)`가 다음 번호를 꺼내 ID 자리에 그대로 넣는다.
- 몇 번이 들어갔는지 자바 쪽은 모른다. 알 필요도 없다.

댓글은 번호를 **먼저 따로 뽑아 두고** 그 값을 INSERT에 쓴다.

```xml
<insert id="save" parameterType="...CommentRequestDTO">
    <selectKey keyProperty="id" resultType="int" order="BEFORE">
        SELECT NEXTVAL(COMMENT_SEQ)
    </selectKey>
    INSERT INTO SPRING_COMMENT_TBL
    VALUES(#{id}, #{comment}, #{email}, #{blogId})
</insert>
```

- `order="BEFORE"`가 INSERT보다 먼저 돌라는 지정이다. 시퀀스는 미리 뽑을 수 있으니 BEFORE다.
- `keyProperty="id"`는 뽑은 값을 **파라미터 객체의 `id` 필드에 넣으라**는 뜻이다.

두 INSERT를 나란히 놓으면 차이가 하나 더 보인다. 글 쪽은 `SPRING_BLOG_TBL(ID, TITLE, ...)`로 컬럼을 적었고, 댓글 쪽은 값만 나열했다. 컬럼을 적지 않으면 **표에 컬럼이 놓인 순서에 기대게 된다.** 순서가 달라지거나 컬럼이 하나 끼어들면 값이 엉뚱한 칸에 들어가고, 타입이 맞으면 오류도 나지 않는다.

왜 굳이 나눠 뽑나. **댓글은 저장한 뒤에 그 번호가 필요하기 때문이다.** 화면은 방금 쓴 댓글을 목록에 끼워 넣어야 하고, 나중에 그것을 지우거나 고치려면 번호로 지목해야 한다. 글은 저장 후 목록 화면으로 이동하므로 번호가 당장 필요 없다.

이 요구가 DTO 모양에도 나타난다. 댓글 요청 DTO에 `id` 칸이 있다.

```java
public class CommentRequestDTO {
    private Integer id ;              // selectKey가 채워 넣을 자리
    private String  comment, email ;
    private Integer blogId ;
}
```

- 요청에는 id를 보내지 않는다. 화면이 보내는 값은 `comment` · `email` · `blogId` 셋뿐이다.
- 이 칸은 **서버가 스스로 채우는 자리**다. 서비스가 저장 직후 `request.getId()`로 그 값을 읽어 컨트롤러로 돌려준다.

### 3. 블로그 하나에 댓글 여럿

글 하나를 열면 댓글이 같이 나와야 한다. 서버가 돌려주는 것은 **글 객체 하나**인데, 그 안에 **댓글 배열**이 들어 있어야 한다는 뜻이다.

응답 DTO가 배열을 품는 구조가 된다.

```java
public class BlogResponseDTO {
    private Integer id ;
    private String  title, content, category, email ;

    //////////////////////////////// blog(1) : comment(N)
    private List<CommentResponseDTO> comments;
}
```

- 관계를 표현하는 자리가 DTO 필드 하나다.
- 댓글이 없는 글이면 이 칸이 비어 있게 된다. 화면은 그 경우도 감당해야 한다.

서버는 조회를 두 번 한다. 글 1건과 그 글의 댓글 N건을 각각 가져와 하나로 합친다.

10일차에는 같은 화면을 흉내용 서버로 만들었고, 그때는 주소에 `?_embed=comments`를 붙이면 관계가 알아서 붙어 나왔다. 그건 그 도구가 제공하는 기능이다. **직접 만든 서버에는 그런 기능이 없으므로 조회를 두 번 해서 손으로 붙인다.**

### 4. 없는 글을 요청하면

주소로 번호를 받는 구조라 **없는 번호가 들어올 수 있다.** 이 경우를 조회 메서드가 타입으로 먼저 알린다.

```java
public Optional<BlogResponseDTO> findById(Integer id);
```

- 반환 타입이 `Optional`이면 **값이 없을 수도 있다**는 뜻이 타입에 적혀 있는 것이다.
- 그냥 `BlogResponseDTO`로 두면 null이 올 수 있다는 사실이 타입만 봐서는 안 보인다.

값이 없을 때 무엇을 할지는 받는 쪽이 정한다.

```java
BlogResponseDTO blog = blogMapper
        .findById(id)
        .orElseThrow(() -> new RuntimeException(id+" BLOG NOT FOUND")) ;
```

- `orElseThrow`는 값이 있으면 꺼내 주고, 없으면 괄호 안의 예외를 던진다.
- 던지는 순간 이 메서드는 거기서 끝난다. 아래 줄로 내려가지 않는다.

여기서 컨트롤러 쪽과 어긋나는 지점이 하나 생긴다.

```java
BlogResponseDTO response = blogService.read(id);

// status code : NOT_FOUND(404), OK(200)
return response != null
        ? ResponseEntity.status(HttpStatus.OK).body(response)
        : ResponseEntity.status(HttpStatus.NOT_FOUND).build();
```

- 서비스가 예외를 던지면 `blogService.read(id)` 자체가 정상적으로 끝나지 않는다. **대입도 일어나지 않고 그다음 줄도 실행되지 않는다.**
- 따라서 `NOT_FOUND` 쪽 가지는 이 구조에서 **닿을 수 없다.** `orElseThrow`를 쓰는 한 `response`가 null인 경우는 생기지 않는다.

> 💡 예외는 값이 아니라서 삼항 연산자로 받아지지 않는다. 조건 분기 앞에서 이미 흐름이 빠져나간다.

### 5. 고치지 않고 복사한다

댓글 목록을 글 객체에 채워 넣는 형태가 코드에 둘 남아 있다. 하나는 조회해 온 객체를 그 자리에서 고치는 것이고, 주석에 `bad case`로 표시돼 있다.

```java
// bad case
// blog.setComments(commentMapper.findByBlogId(blog.getId()));
```

실제로 반환하는 것은 원본을 두고 **댓글만 채운 새 객체를 만드는** 형태다.

```java
return blog.toBuilder()
        .comments(commentMapper.findByBlogId(blog.getId()))
        .build() ;
```

- `toBuilder()`는 기존 객체의 값을 그대로 옮겨 담은 빌더를 만들어 준다. 거기서 바꿀 칸만 덮어쓴다.
- 쓰려면 클래스 쪽에 `@Builder(toBuilder = true)`가 있어야 한다. 옵션 없이 `@Builder`만 붙이면 이 메서드가 생기지 않는다.

왜 고치지 않느냐. 조회 결과를 받은 자리에서 값을 바꾸면 **그 객체가 어디까지 넘어갔는지에 따라 결과가 달라진다.** 값이 변하는 시점이 코드 여러 곳으로 흩어지고, 나중에 "이 값이 언제 채워졌나"를 되짚기 어려워진다. 복사해서 새로 만들면 바뀌는 지점이 이 한 줄로 고정된다.

아예 새로 조립하는 형태도 주석으로 함께 있다.

```java
// case 02
// BlogResponseDTO blog = blogMapper
//         .findById(id)
//         .map( dto -> BlogResponseDTO.builder()
//                         .id(dto.getId())
//                         .title(dto.getTitle())
//                         .content(dto.getContent())
//                         .comments(commentMapper.findByBlogId(dto.getId()))
//                         .build())
//         .orElseThrow(() -> new RuntimeException(id+" BLOG NOT FOUND")) ;
```

- 필드를 하나씩 옮겨 적는다. 무엇이 담기는지 눈에 다 보인다.
- 대신 필드가 늘어날 때마다 옮겨 적을 줄도 늘어나고, 빠뜨리면 그 값만 조용히 비어 나간다. `toBuilder`에는 그 수고가 없다.

### 6. 화면을 스프링으로 갈아끼우기

화면 쪽은 부르는 주소와 보내는 방식만 달라진다. 이전 호출이 주석으로 남아 있어 네 갈래를 나란히 볼 수 있다.

| 화면 | 흉내용 서버 | 직접 만든 서버 | 성공 코드 |
|---|---|---|---|
| 목록 | `GET /blogs` | `GET /blogs/index` | 200 |
| 글쓰기 | `POST /blogs` | `POST /blogs/insert` | 201 |
| 상세 | `GET /blogs/{id}?_embed=comments` | `GET /blogs/read/{id}` + 헤더 | 200 |
| 댓글 등록 | `POST /comments` | `POST /comments/insert` + 헤더 | 201 |

자원 이름만으로 동작하던 주소에 **동작 이름이 붙었다.** 흉내용 서버는 주소 규칙이 정해져 있어 그것을 따르면 되고, 직접 만든 서버는 경로를 내가 정한다.

```js
// await api.get(`/blogs/${id}?_embed=comments`)

// spring boot version
await api.get(`/blogs/read/${id}`, {
            headers : {Authorization : at ? at : "" }
        })
```

- 관계를 붙여 달라는 `?_embed=comments`가 사라졌다. 서버가 이미 합쳐서 준다.
- 토큰은 세 번째 인자의 `headers`에 실린다.

받은 값은 두 갈래로 나뉘어 상태에 들어간다.

```js
if(response.status === 200) {
    setBlog(response.data);
    setComments(response.data.comments) ;
}
```

- 글 본문과 댓글 배열을 각각 다른 상태로 관리한다. 댓글만 바뀔 때 글 본문을 건드리지 않기 위해서다.

댓글 등록이 그 이유를 보여준다. 새 댓글을 쓰면 목록을 다시 불러오지 않고 **배열 끝에 하나만 덧붙인다.**

```js
if(response.status === 201) {
    setComments( ary => {
        return [...ary, response.data]
    });
    setComment('');
}
```

- `response.data`가 방금 저장된 댓글이다. 여기에 **서버가 만든 id가 들어 있어야** 이후 삭제·수정이 그 댓글을 지목할 수 있다.
- 2절에서 `selectKey`로 번호를 미리 뽑은 이유가 여기서 회수된다.

> 💡 목록 전체를 다시 부르지 않으려면 서버가 "방금 만든 것"을 돌려줘야 한다.

## ❓ 몰랐던 것

### 서비스에서 던진 예외를 컨트롤러가 받는가

받지 못한다. 예외는 반환값처럼 건네지는 것이 아니라 **호출한 쪽으로 거슬러 올라간다.** 컨트롤러가 `try-catch`로 감싸지 않으면 그대로 통과해 스프링까지 올라가고, 따로 처리하는 곳이 없으면 500이 나간다.

4절의 코드가 그 상태다. 404를 돌려주려고 적어 둔 가지가 실행되지 않고, 없는 번호를 요청하면 500이 나간다.

실무에서 쓰는 형태는 컨트롤러마다 `try-catch`를 두는 것이 아니라 **예외를 한곳에 모아 처리하는 것**이다. `@RestControllerAdvice`를 붙인 클래스에 `@ExceptionHandler`를 두면, 어느 컨트롤러에서 올라온 예외든 여기서 받아 상태코드를 정해 내보낸다. 이때 `RuntimeException` 대신 뜻이 담긴 예외(예: 글을 못 찾았다는 전용 예외)를 만들어 던지면, 받는 쪽이 그 종류만 보고 404로 매길 수 있다.

정리하면 순서가 이렇다. 서비스는 **"없다"는 사실을 예외로 알리고**, 그 예외를 상태코드로 번역하는 일은 **한곳에 모아 둔 처리기**가 맡는다.

### `readOnly = true`는 무엇을 막는가

조회 메서드에 이 표시가 붙어 있다.

```java
@Transactional(readOnly = true)
public BlogResponseDTO read(Integer id) {
```

이름 때문에 "읽는 동안 다른 쪽이 못 고치게 잠근다"로 읽히기 쉬운데 그런 뜻이 아니다. **이 작업은 쓰기를 하지 않겠다는 표시**이지, 다른 트랜잭션의 수정을 막는 잠금이 아니다.

효과는 무엇을 쓰느냐에 따라 다르다. 값을 자동으로 추적해 바뀐 것을 반영하는 방식(JPA)에서는 그 추적을 건너뛰어 이득이 크다. 지금처럼 SQL을 직접 두고 쓰는 방식(MyBatis)에서는 그 추적 자체가 없어서, 연결에 읽기 전용이라는 힌트를 주는 정도로 작동한다.

그래도 붙일 값은 있다. **의도가 코드에 적힌다.** 이 메서드가 조회만 한다는 것이 표시로 드러나고, 안에서 실수로 저장을 부르면 그것이 규약 위반으로 드러난다.

### setter가 없는데 `selectKey`는 어떻게 id를 넣나

`CommentRequestDTO`에는 `@Setter`가 없다. 그런데 `keyProperty="id"`로 값을 넣으라고 되어 있다.

MyBatis는 값을 넣을 때 setter를 먼저 찾고, **없으면 필드에 직접 넣는다.** 그래서 setter가 없어도 채워진다. 자바 문법으로는 밖에서 못 건드리는 자리를 도구가 리플렉션으로 여는 것이다.

편하지만 대가가 있다. 이 연결은 **컴파일이 잡아 주지 않는다.** 필드 이름을 `id`에서 다른 것으로 바꾸면 XML의 `keyProperty`는 그대로 남고, 컴파일은 통과하며, 실행할 때 가서야 어긋난다.

## 🧑‍💻 바이브코딩 체크

| 상황 | 유의점 | 왜 |
|---|---|---|
| 조회한 객체에 값을 채우는 코드를 받았을 때 | `setXxx()`로 그 자리에서 고치는지, 복사해 새로 만드는지 본다 | 고치는 형태는 값이 변하는 시점이 코드 여러 곳으로 흩어져서, 나중에 "이 값이 언제 채워졌나"를 되짚기 어렵다 |
| 목록에 항목을 덧붙이는 화면을 만들 때 | 서버 응답에 **새 항목의 id**가 들어 있는지 확인한다 | id가 없으면 화면에는 보이지만 그 항목을 지목할 수 없어 삭제·수정이 안 된다 |
| "없으면 404" 같은 분기를 넣을 때 | 그 앞에서 예외를 던지고 있지 않은지 본다 | 예외가 먼저 나가면 분기 줄에 닿지 못해서, 적어 둔 상태코드가 나가지 않는다 |
| 조회 함수의 반환 타입을 정할 때 | 없을 수 있으면 `Optional`로 표시한다 | 그냥 객체 타입이면 값이 없을 수 있다는 사실이 타입에 드러나지 않아 받는 쪽이 대비하지 못한다 |
| 이름으로 연결되는 설정을 고칠 때 | 필드명·XML·매퍼 세 곳을 같이 본다 | 이 연결은 컴파일이 검사하지 않아서, 한쪽만 고치면 실행할 때 가서야 드러난다 |

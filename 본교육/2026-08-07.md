# <LG CNS 6기] 10일차 TIL — 프론트엔드 — 블로그 CRUD 한 벌·1:N 댓글·useMemo

> TL;DR: 어제 골격만 세운 미니 블로그를 **CRUD 한 바퀴**로 닫았다. 글을 쓰고(C) 목록에서 고르고(R) 댓글을 달고(C) 지운다(D). 오늘의 핵심은 **글 하나에 댓글 여러 개가 붙는 1:N 관계**를 서버와 화면에서 어떻게 표현하느냐다.
>
> 📖 **이 글의 사용법**: 수업을 못 들은 사람도 **강사님 코드와 이 글만 있으면 순서대로 따라 만들 수 있게** 썼다. 0단계부터 7단계까지 위에서 아래로 가면 된다. 각 단계는 〈무엇을 만드나 → 어느 파일 → 핵심 코드 → 화면에서 확인하는 법〉 순서다.
>
> ⚠️ **연습용 표시**: 서버는 `json-server`(가짜 백엔드)다. 로그인한 사람이 누구인지도 **브라우저 저장소에 이메일 평문**으로 두고 있다. 실무는 토큰과 서버 검증으로 간다 — 지금은 데이터가 오가는 길을 눈으로 보는 게 목적이다.

## 🗺️ 한눈에 보기

### 오늘은 무엇을 위한 작업이었나

댓글이 달리는 게시판을 떠올리면 된다. **글 목록에서 하나를 눌러 들어가고, 그 글 아래에 댓글을 달고, 내가 쓴 댓글은 지울 수 있다.** 오늘 만든 건 딱 그것이다.

여기서 "한 바퀴"라는 말이 중요하다. 어제까지는 화면을 하나씩 따로 만들었는데, 오늘은 **화면들이 서로를 부르며 원을 그린다** — 목록에서 작성으로 갔다가 다시 목록으로 돌아오고, 목록에서 상세로 들어갔다가 다시 목록으로 나온다.

![블로그 CRUD 한 바퀴](images/2026-08-07-01-크루드한바퀴.png)

| 단계 | 기능 | 화면(파일) | 서버에 보내는 요청 | CRUD |
|:--:|------|------|------|:--:|
| 1 | 글 목록 | BlogIndexPage | `GET /blogs` | R |
| 2 | 카테고리 필터 | BlogIndexPage | (요청 없음 — 받아둔 배열을 거름) | — |
| 3 | 글 작성 | BlogWritePage | `POST /blogs` | **C** |
| 4 | 글 상세 | BlogReadPage | `GET /blogs/:id` | R |
| 5 | 댓글 보기 | BlogReadPage 안 | `GET /blogs/:id?_embed=comments` | R |
| 6 | 댓글 작성 | BlogReadPage 안 | `POST /comments` | **C** |
| 7 | 댓글 삭제 | BlogCommentItem | `DELETE /comments/:id` | **D** |

- 어제 남았던 칸이 오늘 다 찼다. **U(수정)만 아직 없다** — 글·댓글 모두 고치는 화면이 없다.
- 필기에 적힌 그대로 "**이번 토이프로젝트의 핵심은 CRUD 경험**". 화면을 예쁘게 만드는 게 아니라, 네 가지 동작이 서버와 어떻게 짝을 이루는지를 몸에 붙이는 게 목표다.

### 글과 댓글은 어떻게 묶여 있나

오늘 처음 나온 구조다. 지금까지 다룬 데이터는 전부 **한 줄이 한 덩어리**였다(사용자 한 명, 글 한 건). 그런데 댓글은 다르다 — **글 한 건에 댓글이 0개일 수도, 열 개일 수도 있다.**

![글 1건 : 댓글 N건 — blogId로 묶인다](images/2026-08-07-02-일대다.png)

`db.json`을 열어 보면 글과 댓글이 **따로 담겨 있고**, 댓글 쪽이 `blogId`로 자기 주인을 가리킨다.

```json
"blogs": [
  { "id": 1, "title": "요리", "content": "...", "category": "취미", "email": "..." }
],
"comments": [
  { "id": "2",       "blogId": 1, "comment": "냠냠", "email": "haewon@naver.com" },
  { "id": "h2HHzaN", "blogId": "1", "comment": "ㄴㄴㄴ", "email": "win737449@gmail.com" }
]
```

- 댓글이 글 안에 들어가 있지 않다. **댓글은 댓글끼리 모여 있고, 각자 `blogId`라는 이름표로 어느 글 소속인지 밝힌다.**
- 이렇게 나눠 두는 이유는 단순하다 — 댓글을 하나 달 때 **글 전체를 다시 저장할 필요가 없다.** 댓글 한 건만 `comments`에 밀어 넣으면 끝이다.

> 💡 **1:N(일대다) 관계** — 한쪽(글)이 여럿(댓글)을 거느리는 구조. 여럿인 쪽이 **주인의 id를 들고 있는 것**이 규칙이다. 반대로 글이 댓글 id 목록을 들고 있으면, 댓글이 하나 늘 때마다 글을 고쳐야 한다.

## ✍️ 따라 만들기

### 0단계 — 준비물

코드를 치기 전에 **세 가지가 켜져 있어야** 한다. 이게 안 되어 있으면 아래 단계에서 화면이 하얗게 뜨거나 요청이 전부 실패한다.

| 준비물 | 무엇 | 확인 방법 |
|------|------|------|
| json-server | 가짜 백엔드. `db.json`을 읽어 REST API처럼 응답 | 브라우저로 서버 주소 `/blogs`를 열어 JSON이 보이면 OK |
| `.env` | 서버 주소를 담아 두는 파일. `REACT_APP_BACKEND_ENDPOINT=…` | 값을 바꾸면 **개발 서버를 껐다 켜야** 반영됨 |
| 라우트 등록 | 만든 화면을 주소에 연결 | `ToyApp.js`에 `<Route>`가 있어야 주소를 쳐서 들어갈 수 있음 |

📁 `src/api/axios.js` — 서버 주소를 미리 박아 둔 통신 도구. 화면마다 주소를 반복해서 쓰지 않으려고 한 번만 만든다.

```jsx
import axios from 'axios';

const endPoint = process.env.REACT_APP_BACKEND_ENDPOINT;
const api = axios.create({ baseURL: endPoint });

export default api;
```

📁 `src/ToyApp.js` — 오늘 쓸 주소 다섯 개. 주소를 먼저 정해 두면 각 화면이 어디로 이동할지가 명확해진다.

```jsx
<Routes>
  {/* user */}
  <Route path="/"                   element={<SignUpPage />} />
  <Route path="/users/signIn"       element={<SignInPage />} />

  {/* blog */}
  <Route path="/blogs/index"        element={<BlogIndexPage />} />
  <Route path="/blogs/write"        element={<BlogWritePage />} />
  <Route path="/blogs/read/:blogId" element={<BlogReadPage />} />
</Routes>
```

- 맨 아래 `:blogId`가 오늘의 열쇠다. **콜론이 붙은 조각은 고정된 글자가 아니라 "여기에 값이 들어온다"는 자리**다. `/blogs/read/1`로 들어오면 `blogId`가 `1`이 된다.
- 이름을 아무렇게나 지으면 안 된다. **여기 적은 `blogId`라는 이름 그대로** 화면에서 꺼내 쓴다(4단계에서 이것 때문에 막혔다).

> 💡 **CORS — 리액트와 서버가 다른 주소라서 생기는 일**
> 리액트 개발 서버는 `localhost:3000`, json-server는 다른 포트다. 브라우저는 **주소가 조금이라도 다르면 남의 집으로 본다**(포트만 달라도 다른 출처다). 그래서 기본적으로는 요청을 막는다.
> 막지 않으려면 **서버가 "이 주소에서 오는 건 허락한다"고 응답 헤더로 밝혀야** 한다 — 필기에 남긴 응답 헤더의 `Access-Control-Allow-Origin: http://localhost:3000`이 정확히 그 허락이다. json-server는 이걸 기본으로 붙여 준다.
> **preflight(예비 요청)**는 그 앞 단계다. 브라우저가 진짜 요청을 보내기 전에 `OPTIONS`로 "이런 요청 보내도 되냐"고 먼저 물어보는 것. 개발자 도구 네트워크 탭에 요청이 두 번 찍히는 게 이것 때문이다.

### 1단계 — 글 목록 화면

**무엇을 만드나**: 서버에 있는 글을 전부 받아와 카드로 죽 늘어놓는 화면. 카드를 누르면 상세로 들어간다.

이 화면은 **파일 세 개로 쪼개서** 만든다. 한 파일에 다 넣어도 돌아가지만, 나누면 각자 하는 일이 한 가지로 줄어든다.

| 파일 | 하는 일 |
|------|---------|
| `page/BlogIndexPage.jsx` | 서버에서 **가져오기**. 받은 배열을 state에 담아 아래로 내려보냄 |
| `list/BlogList.jsx` | 배열을 **반복해서 늘어놓기**(`map`) |
| `item/BlogItem.jsx` | 카드 **한 장 그리기**. 클릭하면 상세로 이동 |

> 💡 **컴포넌트를 나누면 개발 속도가 오른다** — 필기 첫 줄이다. 왜 빨라지냐면, 카드 모양을 고칠 때 `BlogItem` 한 파일만 열면 되기 때문이다. 한 덩어리로 뭉쳐 있으면 목록 로직과 카드 디자인이 같은 화면에 섞여 있어, 고칠 곳을 눈으로 찾는 시간이 먼저 든다.

**핵심 코드** — 📁 `page/BlogIndexPage.jsx`

```jsx
const [blogs, setBlogs] = useState([]);          // ① 빈 배열로 시작

const loadData = async () => {                   // ② 서버에서 가져오는 함수
  await api.get(`/blogs`)
    .then((response) => {
      if (response.status === 200) {
        setBlogs(response.data);                 // ③ state에 담으면 화면이 따라온다
      }
    })
    .catch((error) => {
      console.log(`debug >>>> axios request error`, error);
    });
};

useEffect(() => { loadData(); }, []);            // ④ 화면이 처음 뜰 때 딱 한 번

// ...
<BlogList ary={filteredBlogs || []} />           // ⑤ 아래로 내려보냄
```

- **왜 빈 배열로 시작하나** — 화면이 그려지는 순간엔 서버 데이터가 아직 없다. `[]`로 시작해야 `map`을 돌려도 안 죽는다. 여기에 `null`을 넣으면 첫 렌더에서 바로 터진다.
- **왜 `useEffect`인가** — 화면을 그리는 함수 안에서 곧바로 `api.get`을 부르면, 데이터를 받아 `setBlogs` → 다시 그림 → 또 `api.get`… 무한 반복이 된다. `useEffect(fn, [])`는 **처음 한 번만** 실행하라는 뜻이다.

📁 `list/BlogList.jsx` — 배열을 받아 카드로 펼친다.

```jsx
const BlogList = (props) => {
  return (
    <Wrapper>
      { props.ary && props.ary.length > 0
          ? props.ary.map((blog, idx) => <BlogItem key={idx} blog={blog} />)
          : '등록된 글이 없습니다.'
      }
    </Wrapper>
  );
};
```

- **`&&`가 아니라 삼항(`? :`)을 쓴 이유** — `{ary.length && <카드들 />}` 로 쓰면 목록이 비었을 때 `0`이 **글자 그대로 화면에 찍힌다**. 삼항은 거짓일 때 그릴 것을 내가 정하므로 그 사고가 안 난다. 게다가 "등록된 글이 없습니다"라는 안내까지 덤으로 생긴다.

📁 `item/BlogItem.jsx` — 카드 한 장.

```jsx
const BlogItem = ({ blog }) => {
  const moveUrl = useNavigate();
  return (
    <Wrapper onClick={() => { moveUrl(`/blogs/read/${blog.id}`); }}>
      {blog.category && <CategoryBadge>{blog.category}</CategoryBadge>}
      <TitleText>{blog.title}</TitleText>
    </Wrapper>
  );
};
```

- **`({ blog })`** — props 객체를 받자마자 `blog`만 꺼내 쓰는 문법(구조분해). `props.blog`라고 쓰는 것과 같은 뜻이다. **한 파일 안에서는 둘 중 하나로 통일**해야 한다(섞으면 `props`가 없다며 조용히 안 그려진다).
- 카드에 붙은 `onClick`이 상세 화면으로 가는 문이다. **주소에 `blog.id`를 실어 보내는 것**이 4단계의 출발점이다.

### 2단계 — 카테고리 필터

**무엇을 만드나**: 목록 위에 〈전체·개발·생활·취미·일상〉 버튼을 두고, 누른 것만 보여준다.

**핵심 코드** — 📁 `page/BlogIndexPage.jsx`

```jsx
const CATEGORIES = ["전체", "개발", "생활", "취미", "일상"];
const [selectedCategory, setSelectedCategory] = useState("전체");

// case02 : useMemo() - 성능개선을 위해서
const filteredBlogs = useMemo(() => {
  return selectedCategory === "전체"
    ? blogs
    : blogs.filter((blog) => blog.category === selectedCategory);
}, [blogs, selectedCategory]);

<CategoryRow>
  {CATEGORIES.map((category) => (
    <CategoryChip
      key={category}
      $active={category === selectedCategory}
      onClick={() => setSelectedCategory(category)}
    >
      {category}
    </CategoryChip>
  ))}
</CategoryRow>
```

- **서버에 다시 묻지 않는다.** 이미 받아둔 `blogs` 배열을 걸러서 보여줄 뿐이다. 그래서 버튼을 눌러도 화면이 깜빡이지 않고 즉시 바뀐다.
- **`$active`의 달러 표시** — styled-components에게 "이건 스타일 계산용이니 실제 HTML 속성으로 내려보내지 말라"는 표시다. 안 붙이면 브라우저가 모르는 속성이라며 콘솔에 경고가 뜬다.
- 필기의 "**css를 쓸 때 active라는 용어. 선택되어 있다**"가 이것이다. 선택 여부를 **참·거짓 하나로 넘기고**, 색은 그 값을 보고 갈라진다.

| 용어 | 내 정리 |
|------|---------|
| `useMemo` | 계산 결과를 기억해 두는 hook. 재료가 안 바뀌면 다시 계산하지 않음 |
| memoization | 그 "기억해 두기" 자체를 부르는 이름 |
| 의존성 배열 | `[blogs, selectedCategory]` — 이 둘이 바뀔 때만 다시 계산 |

> 💡 **왜 그냥 계산하지 않고 `useMemo`인가** — 리액트는 화면에 뭔가 바뀔 때마다 컴포넌트 함수를 **처음부터 다시 실행**한다. 필터 계산이 함수 안에 그냥 있으면, 댓글 입력칸에 글자 하나만 쳐도 전체 목록을 다시 거른다. 지금처럼 글이 몇 건이면 티도 안 나지만, 필기 표현대로 "**대용량의 데이터를 연산**"할 때는 그게 그대로 버벅임이 된다.

- 파일에는 `useMemo`를 안 쓴 판(`case01`)이 **주석으로 남아 있다.** 둘을 나란히 두면 차이가 명확하다 — 계산식은 똑같고, 감싸느냐 마느냐만 다르다.
- 다만 `useMemo`가 공짜는 아니다. 기억해 두는 것 자체에 메모리와 비교 비용이 든다. **가벼운 계산에 다 붙이면 오히려 손해**다. 필기에 "성능 측면에서 매우 중요"라고만 적혀 있지만, 정확히는 "무거운 계산일 때 중요"다.

**확인하는 법**: 카테고리를 눌렀을 때 개발자 도구 네트워크 탭에 **새 요청이 안 뜨면** 제대로 된 것이다(요청이 뜬다면 서버를 다시 부르고 있다는 뜻).

### 3단계 — 글 작성 화면

**무엇을 만드나**: 카테고리를 고르고 제목·본문을 쓴 다음, 저장하면 목록으로 돌아가는 화면.

**핵심 코드** — 📁 `page/BlogWritePage.jsx`

```jsx
const CATEGORIES = ["개발", "생활", "취미", "일상"];   // ← '전체'가 없다

const [title, setTitle]       = useState("");
const [content, setContent]   = useState("");
const [category, setCategory] = useState("");

const writeHandler = async () => {
  api.post("/blogs", { title, content, category, email: user })
    .then((response) => {
      if (response.status === 201) {      // 201 = Created
        moveUrl("/blogs/index");          // 저장 성공 → 목록으로
      }
    })
    .catch((error) => {
      console.log(`debug >>>> axios request error`, error);
    });
};
```

- **`전체`가 빠진 이유** — 목록의 카테고리는 *거르는 조건*이라 "전체"가 필요하지만, 여기 카테고리는 *실제로 저장될 값*이다. "전체"라는 카테고리의 글은 세상에 없다. 같은 이름의 배열이 화면마다 다른 이유가 이것이다.
- **왜 201인가** — 새로 만들어졌을 때 서버가 돌려주는 성공 코드다. 조회(200)와 구분된다. 성공을 한 숫자로 외우지 말고 **2로 시작하면 성공**으로 보는 게 맞다.
- 입력칸은 전부 `value` + `handler` 한 쌍으로 묶여 있다(**controlled component**). 필기의 "**사용자의 keyin이 들어오는 form은 controlled component가 되어야 함. state로 관리**"가 이 모양이다.

> 💡 **입력칸을 왜 state가 쥐어야 하나** — 저장 버튼을 눌렀을 때 "지금 입력칸에 뭐가 들어 있지?"를 알아내야 하는데, state가 쥐고 있으면 그냥 `title` 변수를 보면 된다. state가 없으면 화면에서 입력칸을 찾아 값을 꺼내오는 일을 매번 해야 한다.

**확인하는 법**: 저장 후 목록으로 튕겨 나가고, 방금 쓴 글이 카드로 보이면 성공. 안 보이면 `db.json`을 열어 `blogs` 배열에 들어갔는지부터 본다 — **저장이 안 된 것과 목록이 갱신 안 된 것은 다른 문제**다.

### 4단계 — 글 상세 화면

**무엇을 만드나**: 목록에서 누른 그 글 하나를 펼쳐 보여주는 화면.

여기서 오늘 가장 오래 막혔다. **주소에 실어 보낸 id를 화면에서 어떻게 꺼내느냐**가 문제였다.

![값이 화면 사이를 건너가는 세 가지 길](images/2026-08-07-03-값이건너가는길.png)

**핵심 코드** — 📁 `page/BlogReadPage.jsx`

```jsx
const { blogId } = useParams();                  // ← 라우트에 적은 이름 그대로
const user = localStorage.getItem("user");

const [blog, setBlog] = useState(null);          // 아직 안 왔으므로 null

const loadData = async () => {
  await api.get(`/blogs/${blogId}?_embed=comments`)
    .then((response) => {
      if (response.status === 200) {
        setBlog(response.data);
        setComments(response.data.comments);     // 딸려온 댓글을 따로 담는다
      }
    });
};
useEffect(() => { loadData(); }, []);
```

- **`useParams()`가 돌려주는 이름은 내가 정하는 게 아니다.** `ToyApp.js`에 `/blogs/read/:blogId`라고 적었으니 꺼낼 때도 `blogId`여야 한다. 다른 이름으로 꺼내면 값이 `undefined`가 되는데, **에러가 안 난다** — 서버 요청이 `/blogs/undefined`로 나가고 조용히 실패할 뿐이다.
- 필기에 남긴 그대로 — "**localStorage는 잘 가져오지만 id는 못 가져오는 이유? path variable의 이름인 blogId를 써야 한다.**" 같은 화면에서 로그인 정보(`localStorage`)는 잘 나오는데 글 번호만 안 나오니 더 헷갈렸다. **둘은 전혀 다른 길로 온 값**이라서 그렇다(위 도식).

화면이 뜨기 전을 처리하는 부분도 오늘 추가됐다.

```jsx
{!blog && <Spinner />}
{blog && (
  <Container> ... </Container>
)}
```

- 서버 응답이 오기 전 `blog`는 `null`이다. 그대로 `blog.title`을 읽으면 **화면이 통째로 죽는다.** 그래서 없을 땐 빙글빙글 도는 표시(Spinner)를, 있을 때만 본문을 그린다.
- 어제 갭으로 남긴 "`&&`는 `0`이 화면에 찍힌다" 문제가 여기선 안 생긴다. **`blog`는 `null` 아니면 객체라서 `0`이 될 수가 없다.** `&&`를 쓸 수 있는 안전한 자리와 위험한 자리(개수·길이)가 갈리는 기준이 이것이다.

:::접기 📁 이 단계의 꾸미기 코드(styled-components) — 로딩 스피너 포함
```jsx
const spin = keyframes`

const Spinner = styled.div`

`;
const ContentText = styled.p`
  font-size: 20px;

  white-space: pre-wrap;   /* 줄바꿈(\n)을 화면에서도 줄바꿈으로 */
`;
```

**확인하는 법**: 주소창에 `/blogs/read/1`을 직접 쳐도 같은 글이 떠야 한다. 목록을 거치지 않고도 열리는 게 정상이다 — **주소 자체에 정보가 들어 있기 때문**이다.

### 5단계 — 댓글 보기 (1:N)

**무엇을 만드나**: 글 아래에 그 글의 댓글을 늘어놓는다.

댓글은 `comments`라는 **다른 곳에** 담겨 있다. 그러면 요청을 두 번 보내야 할까? json-server는 한 번에 묶어 주는 방법을 준다.

```jsx
api.get(`/blogs/${blogId}?_embed=comments`)
```

- `?_embed=comments` 한 조각을 붙이면, 서버가 **`blogId`가 이 글을 가리키는 댓글들을 찾아 글 객체 안에 `comments` 배열로 넣어** 돌려준다.
- 그래서 응답 하나에서 두 가지를 꺼낸다 — 글은 `response.data`, 댓글은 `response.data.comments`.

> 💡 **왜 댓글을 따로 state에 또 담나** — 글(`blog`)은 이 화면에서 안 바뀌지만 **댓글은 계속 늘고 준다.** 댓글이 붙었다 지워질 때마다 화면을 다시 그리려면, 댓글 배열이 자기 state를 가지고 있어야 한다. **바뀌는 것과 안 바뀌는 것을 나눠 담는 것**이 기준이다.

📁 `list/BlogCommentList.jsx` — 1단계의 `BlogList`와 판박이다.

```jsx
const BlogCommentList = ({ comments, handler }) => {
  return (
    <Wrapper>
      {comments.map((comment, idx) => (
        <BlogCommentItem
          key={idx}
          comment={comment}
          handler={() => handler(comment.id)}   // 어느 댓글인지 여기서 확정
        />
      ))}
    </Wrapper>
  );
};
```

- **`handler={() => handler(comment.id)}`가 오늘의 요령이다.** 부모(상세 화면)가 만든 삭제 함수는 "어느 댓글"인지 모른다. 목록을 도는 이 자리에서 `comment.id`를 미리 끼워 넣은 새 함수를 만들어 내려보낸다. 그러면 카드는 그냥 누르기만 하면 된다.
- 필기의 "**카드를 선택했을 때 어떻게 key값을 넘길 것인가**"에 대한 답이 이 한 줄이다.

### 6단계 — 댓글 작성

**무엇을 만드나**: 입력칸에 쓰고 버튼을 누르면 댓글이 바로 목록에 붙는다.

```jsx
const [comment, setComment] = useState("");

const commentHandler = async () => {
  const data = { comment, blogId: blog.id, email: user };

  await api.post(`/comments`, data)
    .then((response) => {
      if (response.status === 201) {
        setComments([...comments, response.data]);   // 화면 목록에 한 건 추가
        setComment("");                              // 입력창 비우기
      }
    });
};
```

- **목록을 다시 안 받아온다.** 서버가 돌려준 새 댓글 한 건을 기존 배열 뒤에 붙일 뿐이다. 필기의 "**페이지 전체가 아니라 일부만 리렌더링**"이 이 모양이다.
- **`[...comments, 새것]`으로 새 배열을 만드는 이유** — 기존 배열에 `push`로 밀어 넣으면 배열은 그대로고 안의 내용만 바뀐다. 리액트는 "**같은 배열이네**" 하고 넘어가 화면을 다시 안 그린다. 새 배열을 만들어 줘야 바뀐 걸 알아챈다.
- `setComment("")`가 입력창을 비운다. 입력칸이 controlled component라서 **state를 비우면 화면도 비워진다** — 화면을 직접 건드리는 코드는 한 줄도 없다.

> 💡 **`blogId: blog.id`인 이유** — 주소에서 꺼낸 `blogId`는 **글자**(`"1"`)고, 서버에서 받아온 `blog.id`는 **숫자**(`1`)다. 저장할 때 글자로 넣으면 나중에 숫자로 찾을 때 안 잡힐 수 있다. 실제로 `db.json`에는 `"blogId": "1"`(글자)과 `"blogId": 1`(숫자)이 **섞여 들어가 있다** — 이런 게 쌓이면 "분명 댓글을 달았는데 안 보이는" 상황이 된다.

**⚠️ 지금 코드에 남은 문제**: `commentHandler` 안에 **POST가 두 번** 들어 있다. 앞의 것은 성공 판정을 `200`으로 해 둬서 화면엔 반영되지 않지만, **요청 자체는 이미 나갔기 때문에 서버에는 댓글이 두 건 저장된다.** 화면엔 한 건만 보여서 눈치채기 어렵다 — 따라 만들 때는 **뒤의 것(201 판정) 하나만 남기면 된다.**

### 7단계 — 댓글 삭제 (내 댓글만)

**무엇을 만드나**: 내가 쓴 댓글에만 삭제 버튼이 보이고, 누르면 서버와 화면에서 함께 사라진다.

📁 `item/BlogCommentItem.jsx`

```jsx
const BlogCommentItem = ({ comment, handler }) => {
  const user = localStorage.getItem("user");   // 지금 로그인한 사람

  return (
    <Wrapper>
      <CommentText>{comment.comment}</CommentText>
      {user === comment.email && (            // 내 댓글일 때만 버튼
        <div><Button title="삭제" onClick={handler} /></div>
      )}
    </Wrapper>
  );
};
```

📁 `page/BlogReadPage.jsx` — 실제로 지우는 쪽.

```jsx
const deleteHandler = async (commentId) => {
  await api.delete(`/comments/${commentId}`)
    .then((response) => {
      if (response.status === 200) {
        setComments((ary) => ary.filter((c) => c.id !== commentId));
      }
    });
};
```

- **`filter`로 지운다.** 배열에서 빼는 게 아니라 **지울 것만 빼고 새 배열을 만든다.** 6단계에서 새 배열을 만들어야 화면이 따라온다고 한 것과 같은 이유다.
- `setComments((ary) => …)` — setter에 값 대신 **함수**를 넣는 방식. "직전 값을 받아서 이렇게 바꿔라"는 뜻이라, 지금 화면에 그려진 값이 아니라 **가장 최신 값**을 기준으로 계산한다. 연속으로 여러 번 지울 때 안전하다.

> 💡 **화면에서 버튼을 숨기는 건 보안이 아니다** — `user === comment.email` 검사는 **버튼을 안 보이게 할 뿐**이다. 개발자 도구로 요청을 직접 보내면 남의 댓글도 지워진다. 진짜 검사는 서버가 해야 한다. 지금은 json-server라 그 층이 아예 없다(연습용 구조).

**확인하는 법**: 다른 이메일로 쓴 댓글에는 삭제 버튼이 안 보여야 한다. `db.json`의 댓글 `email`을 손으로 바꿔 보면 버튼이 나타났다 사라진다.

## 🧩 오늘의 자리 — 어디서 와서 어디로 가나

- **어제**(9일차)는 미니 블로그의 골격 — 목록까지만 돌고 작성·상세는 빈 파일이었다. 오늘 그 칸이 다 찼고 **댓글이라는 새 층**이 얹혔다.
- **1:N 관계**는 오늘 처음이지만 앞으로 계속 나온다. 게시판–댓글, 주문–주문상품, 사용자–게시글 — 업무 시스템 데이터는 거의 다 이 모양이다. 지금은 `?_embed=` 한 조각이 대신해 주지만, **백엔드 과목에서 SQL의 `join`으로 다시 만난다.** [예측]
- `useMemo`는 hook 최적화 묶음의 첫 칸이다. 필기의 "**현업에서는 hook이 매우 중요**"가 예고다 — `useCallback`·`React.memo`가 같은 묶음이고, 아직 안 배운 **사용자 정의 hook**도 이 줄기다. [예측]
- 남은 칸은 **U(수정)**. CRUD 네 글자 중 하나만 비어 있다. [예측]

## ❓ 몰랐던 것

**주소에서 꺼내는 이름을 내가 못 정한다는 걸 몰랐다.** `useParams()`로 값을 꺼내려면 라우트에 적은 `:blogId`와 **글자 하나까지 같아야** 한다. 같은 화면에서 `localStorage`는 멀쩡히 나오는데 글 번호만 `undefined`가 나오니 원인이 엉뚱한 데 있는 줄 알았다. 정리하고 보니 둘은 **완전히 다른 길로 온 값**이다 — 주소는 URL을 타고, 로그인 정보는 브라우저 저장소에서 온다.

**여러 파일을 오가는 흐름이 안 잡혔다.** 필기에 "**hook 활용을 해서 여러 파일을 왔다갔다하는데 솔직히 흐름이 잘 안 잡힘. 추후 복습이 필요**"라고 적었다. 이 글을 단계 순서로 쓴 게 그 답이다 — 화면 단위가 아니라 **만드는 순서**로 늘어놓으니, 어느 파일이 어느 파일을 부르는지가 한 줄기로 보인다.

**memoization을 처음 들었다.** 계산 결과를 기억해 뒀다가 재료가 안 바뀌면 다시 계산하지 않는 것. `useMemo`가 그 도구다. 지금 데이터로는 효과가 눈에 안 보이는데, 그게 정상이다 — **무거운 계산에서만 값을 한다.**

**CORS와 preflight는 아직 반쯤이다.** 필기에도 "잘은 모르겠음"이라 적었다. 브라우저가 다른 출처의 요청을 막고, 서버가 응답 헤더로 허락한다는 큰 그림까지는 잡혔다. 다만 **어떤 요청이 preflight를 유발하는지**(단순 요청과 그렇지 않은 요청의 경계)는 아직 흐리다 — 🔍에 정리해 뒀지만 코드로 확인한 건 아니다. 🚧

**목록에서도 댓글을 같이 받아와야 하나?** 필기의 물음표 그대로다. `?_embed=comments`를 목록 요청에도 붙이면 화면에 안 보이는 댓글까지 전부 받아온다. **화면에 필요한 만큼만 받는 게 기본**이고, 목록에 댓글 수를 표시해야 한다면 그때 다시 판단할 문제다. 🚧

## 🧑‍💻 바이브코딩 체크

| 상황 | 유의점 | 왜 |
|------|--------|-----|
| 데이터가 1:N일 때 | **여럿인 쪽에 주인 id**를 둔다 | 반대로 하면 댓글 하나 늘 때마다 글을 고쳐야 한다 |
| id를 저장할 때 | **글자냐 숫자냐를 처음에 정한다** | 섞이면 "분명 넣었는데 안 나오는" 버그가 된다 — 오늘 `db.json`이 실제로 그 상태 |
| AI에게 목록 화면을 시킬 때 | **조달·배치·표시 3층으로 나눠 달라**고 명시 | 한 파일로 주면 카드 디자인만 고치려 해도 통신 코드를 헤집게 된다 |
| 목록을 갱신할 때 | 재조회 / 배열에 추가 중 **골라야 한다** | 혼자 쓰는 화면은 추가로 충분, 여럿이 쓰면 남의 글이 안 보인다 |
| 배열 state를 바꿀 때 | `push` 말고 **새 배열**(`[...ary, 새것]`·`filter`) | 리액트는 "같은 배열"이면 화면을 다시 안 그린다 |
| 권한을 화면에서 가릴 때 | **숨기는 것은 막는 것이 아니다** | 버튼을 안 보여도 요청은 보낼 수 있다 — 서버 검사가 진짜 방어선 |
| 최적화 도구(`useMemo` 등) | **무거운 계산에만** | 가벼운 계산에 다 붙이면 기억해 두는 비용이 더 든다 |

## 🔍 추가로 찾아본 것

**preflight는 모든 요청에 붙지 않는다.** 오늘 네트워크 탭에 요청이 두 번 찍힌 게 궁금해서 찾아봤다. `GET`이면서 특별한 헤더가 없는 "단순 요청"은 예비 요청 없이 바로 나가고, `DELETE`처럼 서버 데이터를 바꾸는 메서드나 `Content-Type: application/json`이 붙은 요청은 **먼저 `OPTIONS`로 허락을 받고** 나간다. 오늘 댓글 작성·삭제가 여기 해당한다.
- MDN CORS: https://developer.mozilla.org/ko/docs/Web/HTTP/Guides/CORS
- MDN preflight: https://developer.mozilla.org/ko/docs/Glossary/Preflight_request

**`_embed`는 json-server에만 있다 — 운영에선 이 자리가 문제 지점이다.** 실제 서버라면 글과 댓글을 `join`으로 묶거나, 요청을 두 번 보내야 한다. 두 번 보내는 쪽을 택하면 **목록 20건에 각각 댓글을 물어보느라 요청이 21번** 나가는 상황이 생긴다(흔히 N+1 문제라 부른다). 배포해서 쓰는 앱(adsp-board)도 Supabase에서 관련 데이터를 한 번에 가져오게 쿼리를 짜 두는데, 오늘 `?_embed=`가 그 자리를 미리 보여준 셈이다. **학습용 도구가 대신해 주는 자리가 어디인지 알아 두는 게, 나중에 그 자리를 직접 만들 때 헤매지 않는 방법이다.**

**삭제 성공 코드는 200일 수도 204일 수도 있다.** 코드 주석에는 `204(No_Content)`라 적혀 있는데 실제 판정은 `status === 200`으로 되어 있다. json-server는 삭제 후 빈 객체와 함께 200을 주기 때문에 지금은 이게 맞다. 다만 **서버가 바뀌면 이 줄이 조용히 안 먹는다** — 204를 주는 서버로 옮기면 삭제는 되는데 화면에서만 안 사라진다. 성공 판정을 `>= 200 && < 300`처럼 묶음으로 두는 편이 안전하다.
- MDN 204 No Content: https://developer.mozilla.org/ko/docs/Web/HTTP/Reference/Status/204

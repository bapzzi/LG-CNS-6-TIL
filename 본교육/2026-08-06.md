실습 코드의 파일 구조를 기능 기준으로 재구성한 표. 오늘 어디까지 왔는지가 한눈에 보인다.

| 기능 | 파일 | 오늘 상태 |
|------|------|-----------|
| 주소 설계 | ToyApp.js | ✅ 라우트 5개 확정(`/`=회원가입이 첫 화면) |

| 글 작성 | features/blog/page/BlogWritePage.jsx | 🚧 골격만 — 입력칸·버튼 배치, 저장 로직 없음 |

## ✍️ 공부한 내용

### 1. 전체 흐름 — 로그인부터 글 목록까지

세부에 들어가기 전에 큰 그림. 사용자가 로그인하면 글 목록이 뜨기까지, 파일 네 개를 데이터가 이렇게 건너간다.

![로그인부터 글 목록까지 — 데이터 흐름](images/2026-08-06-04-데이터흐름.png)

| 층 | 파일 | 역할 |
|----|------|------|
| page | BlogIndexPage | **데이터 조달** — 서버에서 배열을 받아 state에 담고 아래로 내려보냄 |
| list | BlogList | **배치** — 받은 배열을 `map`으로 돌려 한 건씩 넘김 |
| item | BlogItem | **한 건 표시** — 지금은 `blog.title` 한 줄이 전부 |

> 💡 서버와 왕복하는 건 page 층뿐이다. list와 item은 **props로 받은 것을 그리기만** 한다 — 그래서 아래층일수록 단순하고, 재사용하기 쉽다.

- 주소 설계도 이 흐름의 일부다. ToyApp.js의 라우트 5개가 기능 표의 번역이고, 주석(`{/* user */}`, `{/* blog */}`, `{/* blog - comment */}`)으로 구역을 먼저 갈라 두고 채워 가는 모양이다 — comment 구역은 아직 비어 있다.

### 2. 회원가입 — form 여러 칸을 state 하나로

어제 필기에 물음표로 남긴 **"useState를 객체로 묶는 법"**이 여기서 풀렸다. 이름·이메일·비밀번호 세 칸을 칸마다 state로 두지 않고 객체 하나로 묶는다.

| 용어 | 내 정리 |
|------|---------|
| controlled component | 입력칸 값을 state가 쥐는 것. `value` + `onChange` 한 쌍 |
| computed property key | `[name]: value` — 대괄호 안 **변수의 값**이 객체의 키 이름이 됨 |

```jsx
const [form, setForm] = useState({ name: '', email: '', password: '' });

// 기존값을 유지하면서 현재 입력된 필드의 상태변화를 처리
const keyHandler = (e) => {
  const { name, value } = e.target;
  setForm({ ...form, [name]: value });
};

<Input type='email' name='email' value={form.email} onChange={keyHandler}/>
```

- **왜 합치나** — 칸마다 state+setter+핸들러를 두면 입력칸이 하나 늘 때마다 고칠 곳이 서너 군데다. 객체로 묶으면 input에 `name` 속성 하나만 추가하면 끝. 수업 표현 그대로 "**실수를 줄일 수 있음**" — 고칠 곳의 개수 자체가 줄기 때문이다.
- 핸들러 하나가 모든 칸을 받는 열쇠가 `[name]: value`다. `e.target.name`이 `"email"`이면 `email` 키가, `"password"`면 `password` 키가 갱신된다. **어느 칸에서 온 이벤트인지를 name이 말해 준다.**
- **왜 `...form`을 먼저 펴나** — setter는 병합이 아니라 **교체**다. 안 펴면 방금 친 칸 하나만 남고 나머지 키가 통째로 사라진다.
- 제출은 버튼이 아니라 **form의 `onSubmit`**에 걸었다. 버튼 클릭 외에 **Enter 제출**도 같은 길로 들어온다 — 어제 "버튼 기본 type=submit" 갭의 연장으로, 기본 동작을 막기만 하는 게 아니라 **한 입구로 모으는** 용도.

저장은 axios POST. 성공과 실패의 길이 갈린다:

```jsx
await api.post('/users', data)
        .then( response => {
            if( response.status === 201) {
                moveUrl('/users/signIn');     // 성공 → 로그인 화면으로 이동
            }
        })
        .catch( error => { ... })             // 실패(4xx) → 현재 페이지에서 처리
```

- **axios는 2xx 응답만 `then`으로 보내고, 4xx·5xx는 `catch`로 던진다.** 그래서 성공/실패 분기가 if문이 아니라 then/catch 모양이 된다.
- 필기엔 "성공(200)"으로 적었는데 코드 주석은 **"가입성공시(201)"** — POST로 새로 만들어지면 200이 아니라 **201(Created)**이다. 성공은 한 값이 아니라 **2xx 묶음**으로 본다.

### 3. 로그인 — 조회는 QueryString, 로그인 상태는 localStorage

회원가입이 "데이터를 **보내는**(POST)" 쪽이었다면, 로그인은 "조건에 맞는 사용자가 **있는지 물어보는**(GET)" 쪽이다.

```jsx
await api.get(`/users?email=${form.email}&password=${form.password}`)
        .then( response => {
            if(response.status === 200) {
                localStorage.setItem('user', response.data[0].email);
                // 추후: 인증·인가 -> JWT or spring security
                moveUrl('/blogs/index');
            }
        })
```

- **QueryString** = URL 뒤에 `?키=값&키=값`으로 조건을 직접 싣는 방식. json-server가 이걸 받아 "email과 password가 둘 다 일치하는 행"을 걸러 준다. 코드 주석에는 같은 일을 하는 SQL(`select … where email = ? and password = ?`)이 나란히 적혀 있다 — 지금 URL 한 줄이 백엔드에선 이 쿼리가 된다는 예고다.
- 다른 쓰는 법도 있다: `api.get('url', { params: { email: …, password: … } })` — axios가 객체를 QueryString으로 만들어 붙여 준다. 조건이 많아지면 이쪽이 안 깨진다.
- **로그인 "상태"는 어디에 남나** — `localStorage`. 브라우저에 남는 키-값 저장소라 새로고침해도 살아 있고, BlogIndexPage가 `getItem('user')`로 꺼내 "○○님 환영합니다"를 그린다. 페이지 사이를 넘어 살아야 하는 값이라 state가 아니라 localStorage에 둔 것.
- 주석의 "인증·인가 → JWT or spring security"는 예고다. 지금은 이메일 평문을 그대로 저장하는 **연습용 구조**(TL;DR의 경고가 이것) — 실무는 서버가 발급한 토큰을 저장하고, 요청마다 헤더에 실어 보낸다.

### 4. 글 목록 — 조달 · 배치 · 표시

1절 흐름의 세부. 조달부(BlogIndexPage)에 오늘 배운 조각이 다 들어 있다:

```jsx
const [blogs, setBlogs] = useState([]);

const loadData = async () => {
  await api.get(`/blogs`)
          .then( response => {
              if(response.status === 200) {
                  setBlogs(response.data);   // 받은 배열을 state로 → 화면이 따라옴
              }
          })
}
useEffect(() => { loadData(); }, []);        // 마운트 1회만 조회

<BlogList ary={blogs || []}/>                 // 아래로 내려보냄
```

- 파일에는 주석 처리된 **하드코딩 더미 배열**이 남아 있다. 순서가 읽힌다: ① 가짜 데이터로 화면 모양부터 확인 ② 그 다음 axios 조회로 교체. 데이터 문제와 화면 문제를 한 번에 안 섞는다.
- 파일의 주석 그대로 — "**렌더링 시점에 데이터 바인딩이 X, side effect 필요함!!**". 컴포넌트 함수가 처음 실행되는 순간엔 서버 데이터가 아직 없다. 그래서 일단 빈 배열로 그리고, `useEffect`(8일차)가 마운트 후 조회해서 `setBlogs`로 신고하면 그때 다시 그린다. **빈 화면 → 데이터 도착 → 다시 렌더**가 정상 동작이다.

받는 쪽(BlogList)은 어제 배운 조건부 렌더링으로 닫는다:

```jsx
{   props.ary && props.ary.length > 0 ?
    props.ary.map((blog, idx) => {
        return <BlogItem key={idx} blog={blog} />
    })
    :
    '등록된 글이 없습니다.'
}
```

- 어제 갭으로 남긴 "`{list.length && <A />}`는 빈 목록에서 `0`이 찍힌다"가 여기서 답을 만났다 — **`&&`가 아니라 삼항(`? :`)으로 쓰면** 거짓일 때 그릴 것을 직접 정하므로 `0`이 샐 자리가 없다. 게다가 "등록된 글이 없습니다"라는 안내까지 생긴다.

> 💡 조달(page) / 배치(list) / 표시(item)를 나누는 이유 — 카테고리 필터 같은 기능은 **데이터를 쥔 곳**에만 붙일 수 있다. 데이터가 page에 있으니 필터도 page에서 하고, list는 걸러진 결과를 받아 그리기만 한다. **state를 어디 두느냐가 다음 기능의 자리를 정한다.**

- 글 작성(BlogWritePage)은 카테고리 칩·제목·본문 입력칸·버튼까지 **배치만** 돼 있고 저장 로직이 없다. 글 보기(BlogReadPage)는 빈 파일. 화면 골격부터 세우고 로직은 다음에 붙이는 순서다.

### 5. 댓글 하나 달았는데 화면 전체를 다시 받아올 것인가

수업에서 명시적으로 던져진 고민 — "전부 렌더링할 것인가 일부만 할 것인가".

| 방식 | 코드 | 비용 | 한계 |
|------|------|------|------|
| 전체 재조회 | 등록 후 `GET /comments` 다시 | 서버 왕복 +1 | 항상 최신 |
| state에 추가 | `setComments([...comments, response.data])` | 왕복 없음 | 남이 단 댓글은 안 보임 |

- state에 추가하는 쪽이면, POST 응답으로 돌려받은 **새 댓글 한 건만 state에 붙이고** React가 바뀐 목록 부분만 다시 그린다(6일차 버추얼 돔이 여기서 일한다).
- 어느 쪽이 정답이 아니라 **서로 주고받는 것이 있는 선택(트레이드오프)**이다. 나 혼자 보는 목록이면 추가로 충분하고, 여럿이 동시에 쓰는 화면이면 재조회(또는 다른 동기화 수단)가 맞다. "고민"이라고 표현된 이유가 이것이다.

### 6. MVP로 가는 이유 — AI판과 손코딩판이 한 파일에

SignUpPage 파일 아래엔 `// gen ai agent code`라는 주석으로 **AI가 만든 판 전체가 주석 처리된 채** 붙어 있다. 위쪽의 손코딩판과 나란히 놓고 보면:

| | 손코딩판 | AI판(주석 보관) |
|---|---|---|
| 분량 | ~150줄 | ~300줄 |
| 기능 | 입력 → POST → 이동 | + 유효성 검사·에러 문구·비밀번호 보기 토글·아이콘 |
| 목적 | **흐름이 보이게** | 완성도 |

- AI판이 나쁜 코드가 아니다 — 오히려 실무형에 가깝다. 문제는 **배우는 단계에서 저걸 받으면 어느 줄이 뼈대이고 어느 줄이 살인지 구분이 안 된다**는 것. 오늘 실습도 AI를 활용해 빠르게 완성해 봤지만, 완성만 있고 흐름 파악이 비었다는 게 하루의 반성이다.
- 그래서 방침: 앞으로는 **MVP로 기본 틀을 잡는 것에 초점** — BlogList·BlogItem처럼 아주 기초적인 것부터, UI와 부가 기능은 나중에. 지금 중요한 건 각 파일이 어떻게 유기적으로 얽히는지고, TIL도 흐름을 가장 앞에 둔다. 이 글이 1절부터 흐름으로 시작한 이유다.

- 미니 블로그 자체도 남은 칸이 명확하다 — 글 작성·글 보기 완성, 그리고 U·D(수정·삭제). [예측]

## ❓ 몰랐던 것

**useState를 객체로 묶는 법을 몰랐다(어제 🚧).** 오늘 수업이 그 답이었다 — form 객체 하나 + `[name]: value` 공용 핸들러. 어제는 칸마다 state를 쪼갰는데, 오늘 그 방식이 "칸이 늘면 실수가 는다"는 이유와 함께 대체됐다.

**필기의 "keyhandler"가 특별한 개념인 줄 알았다.** 실습 코드를 열어 보니 핸들러 **함수 이름이 `keyHandler`**였을 뿐 — 하는 일은 onChange 핸들러다. 필기가 흐릴 땐 추측하지 말고 **코드 원본을 열면** 바로 끝난다.

**성공 코드가 200 하나가 아니다.** 필기엔 "성공(200)"으로 적었지만 POST 성공은 **201(Created)**. 판정은 "2xx면 성공" 층으로 본다 — axios가 2xx만 `then`으로 보내주는 것도 같은 결.

**이벤트 버블링을 어제 흘려보냈다.** 필기에 "어제 나온 개념인데 제대로 못 봤음"으로 남긴 것 — 자식 요소의 클릭이 부모 요소로 차례로 **전파**되는 동작이다. 오늘 구조로 말하면: 글 카드 전체가 클릭(글 이동)인데 그 안에 삭제 버튼을 넣으면, 삭제를 눌러도 클릭이 부모까지 올라가 **글 이동까지 같이** 일어난다. 막는 문이 `e.stopPropagation()`. 삭제 기능이 다음 차례라 곧 실전으로 만난다.

## 🔍 추가로 찾아본 것

**localStorage에 로그인 정보를 두는 건 어디까지 괜찮은가.** 오늘 구조(이메일 평문 저장)는 연습용이고, 실무에서도 토큰을 localStorage에 두는 방식 자체가 논쟁거리다 — JS로 누구나 읽을 수 있어서(XSS에 노출되면 토큰이 통째로 샌다), 서버만 읽는 HttpOnly 쿠키와 비교된다. 운영 중인 앱(adsp-board)의 Supabase 로그인도 결국 이 저장 문제를 라이브러리가 대신 풀어주고 있던 것 — 어디에 저장하는지 확인해 볼 것.
- MDN localStorage: https://developer.mozilla.org/ko/docs/Web/API/Window/localStorage
- MDN 이벤트 버블링: https://developer.mozilla.org/ko/docs/Learn_web_development/Core/Scripting/Event_bubbling

**`response.data[0]`은 한 계단을 건너뛴다.** 로그인 코드는 200 확인 후 바로 `data[0].email`을 읽는다 — 어제 정리한 "조회 성공 ≠ 대상 존재" 그대로, 조건에 맞는 사용자가 없어도 조회는 성공(200)이라 빈 배열이면 `data[0]`이 undefined가 되어 여기서 죽는다. `data.length > 0` 체크가 필요한 자리가 정확히 여기다. 내 코드엔 넣는다.

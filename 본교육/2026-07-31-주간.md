## 흐름 따라 복기 — 닷새가 한 줄로 이어진다

한 주를 요약하면 **"서버에서 데이터를 받아 화면을 만드는 SPA" 한 문장을 닷새에 걸쳐 분해한 것**이다.

### 1. 왜 이 언어들인가 (07-27)

- 특강일에 본교육 4언어(Java·JavaScript·SQL·YAML)를 계보로 정리. 기준 = 앞 언어의 한계가 다음 언어를 만든다.
- ABAP 경험 기준의 거리 재기: Java·SQL은 가깝고(강한 타입·SELECT), JavaScript의 동적 타입·**비동기**와 YAML의 인프라 코드화는 새로 배울 영역.
- 이 주에 그 "새로 배울 영역" 첫 번째(JavaScript·비동기)를 정면으로 통과했다.

### 2. 갈림길 — 응답에 무엇이 오는가 (07-28)

- 웹은 요청–응답 한 쌍으로 돈다. 개발 방식이 갈리는 지점은 응답의 **내용물**.
  - 풀브라우징: 요청마다 완성된 페이지를 새로 받음.
  - SPA: 껍데기는 처음 한 번, 이후엔 **데이터(JSON)만**. 화면 교체는 브라우저 안의 컴포넌트 담당.
- 로그인 폼을 만들어 제출해보니 마스킹해 둔 비밀번호가 주소창에 그대로 떴다(`?email=...&pswd=dddd`). form 제출 = 입력값을 queryString에 실어 페이지째 이동하는 고전 방식 — SPA가 form 대신 script와 JSON으로 가는 이유를 주소창 한 줄로 확인.

### 3. 옛 방식을 몸으로 — CSS와 풀브라우징 폼 (07-29)

- CSS 기본기: 선택자 5종+조합(`>`·띄어쓰기·`,`), 박스 모델(구분 기준=**border** — 안쪽 여백 padding, 바깥 margin), display 3종(block/inline/inline-block).
- 예약 폼 실습으로 풀브라우징을 한 바퀴: input의 `name`이 queryString의 key가 되고, `method="get"`이라 값이 주소에 실린다. 화면마다 html 파일이 하나씩 필요.
- 여기서 생긴 판별법 — **html 파일 개수와 URL 형태만으로 풀브라우징/SPA를 구분할 수 있다.** 파일이 index 하나뿐이고 주소가 안 바뀌면 SPA.
- 프레임워크 vs 라이브러리 = 제어 주체의 차이. 스택 구성도 하나의 결정 사항이라, 지정하지 않으면 임의로 정해진다는 것까지.

### 4. 화면을 코드로 — DOM·이벤트·단방향 (07-30)

- 좌표가 먼저: 3계층(Presentation / Business / Persistence) 중 지금까지 배운 전부는 **Presentation 안**.
- 부품을 순서대로 — 넣을 그릇(객체·배열) → 만질 대상(DOM/BOM) → 도구(함수·map·filter·reduce) → 출구(문자열 조립 → `innerHTML`로 한 번에 꽂기).
- 전날 손으로 4번 복사해 만든 카드 화면을, 이날은 배열 하나와 `forEach` 세 줄로 만들었다. **같은 구조가 반복되면 데이터로 만들어 코드가 그리게 한다.**
- 그리고 한계 — `.value`에 **할당하는 것이 곧 렌더링**인데, 데이터를 나중에 바꿔도 화면은 그대로다(**단방향**). 갱신을 사람이 챙겨야 하는 구조. 이 수동 갱신을 자동으로 바꿔주는 것이 reactive state고, React가 필요한 이유가 여기서 닫혔다.

### 5. 데이터가 도착하다 — Promise·fetch·axios (07-31)

- **비동기 = 요청을 보내두고 할 일을 계속하는 것.** 기다리며 멈추면(동기) 서버가 느린 날 화면 전체가 얼어붙는다. "도착하면 이걸 해라"의 예약이 then, 그 자리에서 기다려 받는 게 await.
- **Promise = 결과가 아니라 결과가 담길 상자.** 찍는 시점에 따라 pending → fulfilled/rejected로 다르게 보인다.
- fetch의 then이 두 번인 이유 — response는 데이터가 아니라 **봉투**고, `.json()`으로 여는 작업도 Promise를 돌려준다. axios는 이 단계를 없애고 `response.data`에 바로 담아준다 — 손으로 겪은 다음에 도구를 받는 순서.
- 삭제 실습에서 이틀 연속 같은 벽: 배열에서 지워도(splice) 화면은 그대로(단방향). 서버에서 다시 받으면(재조달) 삭제가 무효가 되고, 지금 배열로 다시 그려야(재렌더) 성공. **재조달과 재렌더는 다른 일이다.**
- 그리고 회수 — 전날 하드코딩해 둔 `user` 객체 자리에 fetch·axios 응답이 실제로 들어왔다. 통신은 Presentation과 Business를 잇는 선.

## 이번 주 가장 큰 트러블슈팅 — "에러 없이 조용히 틀린다"

한 건을 꼽는 대신 한 **패턴**을 꼽는다. 이번 주 막힌 자리 대부분이 같은 얼굴이었다 — **에러가 안 나는데 결과만 틀리다.**

| 자리 | 무엇이 조용했나 |
|------|----------------|
| CSS 단위 없는 값 (07-29) | `margin: 5 30 10 15px` — 선언 전체가 무시되는데 오류 표시가 없음 |
| 따옴표 안의 `${변수}` (07-30) | `${}`는 백틱 안에서만 해석. 큰따옴표에 쓰면 글자 그대로 남고 에러도 없음 |
| `reduce` 초기값 누락 (07-30) | 마지막 `, {}`가 없으면 첫 요소가 상자로 쓰여 엉뚱한 키가 섞임 — 값만 틀림 |
| 존재하지 않는 속성 이름 (07-30) | `texContent` 오타에 할당해도 조용히 넘어감 — 엉뚱한 속성이 하나 생길 뿐 |
| HTML 속성 이벤트의 함수명 불일치 (07-30) | 로딩 시점엔 조용하고, 버튼을 눌러야 "그런 함수 없다"가 남 |
| await 누락 (07-31) | 데이터 도착 전에 그리면 빈 배열로 그려짐 — **에러 없이 빈 화면** |

- 깊게 본 건 reduce. 초기값 유무로 직접 실행해 대조했다:

```
초기값 없음: {"email":"naver.com","nickName":"IronMan","google.com":"Bob",...}
초기값 있음: {"naver.com":"IronMan","google.com":"Bob","daum.com":"Alice"}
```

- 원인이 다 같다 — CSS는 이해 못 하는 줄을 건너뛰고 계속 그리도록 설계됐고(옛 브라우저 호환), JS도 없는 속성 할당·해석 안 되는 문자열을 허용한다. 유연함의 대가가 침묵.
- **재발 방지 = "에러가 없다"를 "정상이다"로 읽지 않기.** 결과를 눈으로 확인하는 단계를 코드 실행마다 붙인다. 이번 주에만 여섯 번 걸렸으면 습관으로 만들 값어치가 있다.

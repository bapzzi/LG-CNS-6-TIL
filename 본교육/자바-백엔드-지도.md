## 1. 골격 — 요청 하나가 지나는 길

```
사용자 입력
  ↓
View                사람과 만나는 유일한 층
  ↓  요청 이름표(endPoint)
FrontController     모든 요청의 단일 입구
  ↓  담당자 조회(DL)
Factory             이름표 → 담당 객체. 싱글톤으로 하나만
  ↓
Controller          요청 하나를 전담
  ↓
Service (인터페이스) / ServiceImpl (구현)     업무 규칙
  ↓
Dao / Repository    데이터 보관소와 대화
  ↓
DB (지금은 ArrayList)

← 돌아오는 길은 DTO에 담겨 같은 경로를 거꾸로
```

**3계층으로 묶으면** Presentation(Controller까지) · Business(Service) · Persistence(Dao).

**두 방향의 규칙**
- 요청은 위에서 아래로만 간다. 층을 건너뛰지 않는다.
- 각 층은 자기 **바로 아래**만 안다. View는 Dao의 존재를 모른다.
- 아래층을 만드는 것은 자기 자신이 아니라 **팩토리**다(DI).

## 4. 자주 헷갈리는 짝

| 짝 | 무엇이 다른가 |
|---|---|
| **DI vs DL** | DI는 넣어 준다(팩토리가 생성자로). DL은 꺼내 온다(`getBean()`). 받는 쪽이 움직이는지 여부 |
| **throws vs throw** | throws는 선언부의 표지판. throw는 안에서 실제로 터뜨리는 동작 |
| **Stream API vs InputStream** | 앞은 컬렉션 가공 사슬, 뒤는 데이터가 지나는 통로. 이름만 같다 |
| **casting vs parsing** | 캐스팅은 이미 숫자인 값의 타입 변경. 파싱은 글자를 읽어 숫자를 새로 만드는 것 |
| **Service vs ServiceImpl** | 앞은 무엇을 할 수 있는지(인터페이스), 뒤는 어떻게 하는지(구현) |
| **DTO vs Entity** | 층 사이를 오가는 그릇 vs DB와 붙는 자리에서만 쓰는 그릇 (예정) |

## 5. 에러가 났을 때 어느 층인지 좁히는 법

스택 트레이스는 **맨 위가 사고 지점**, 아래로 갈수록 부른 쪽이다. 아래에서 위로 읽으면 요청이 지나온 길 그대로다.

| 증상 | 먼저 볼 층 |
|---|---|
| 화면이 이상하다 | View |
| 값이 이상하다 | Service |
| 데이터가 아예 없다 | Dao |
| `NullPointerException` | 죽은 층이 아니라 **그 객체를 만들어 넣는 곳**(Factory) |

# <LG CNS 6기] 개발 언어 계보 정리 — ABAP 경험 기준

> TL;DR: 본교육에서 배울 Java·JavaScript·SQL·YAML을 계보 순서로 정리했다. 기준은 "앞 언어의 한계가 다음 언어를 만든다"는 흐름이다. ABAP을 배운 경험이 있어 각 언어마다 ABAP과의 공통점·차이를 함께 적었다. 정리 결과, Java·SQL은 ABAP 경험과 겹치는 부분이 많고, JavaScript의 동적 타입·비동기와 YAML의 인프라 정의는 새로 배워야 하는 영역이다.

---

## 0. 문서 목적

본교육 6개월간 Java, JavaScript, SQL, YAML을 배운다. 경영학부에 SAP(ABAP) 경험만 있는 입장에서, 문법을 하나씩 외우기 전에 이 언어들이 왜 존재하고 서로 어떤 관계인지를 먼저 정리해둔다.

언어를 볼 때 기준으로 삼을 질문은 세 가지다. 이 문서는 이 세 질문으로 각 언어를 정리했다.

| 질문 | 뜻 |
|------|-----|
| **① 데이터를 어떻게 저장하는가** | 타입을 미리 선언하는가(강한 타입), 실행 중에 정해지는가(동적 타입) |
| **② 데이터를 어떻게 처리하는가** | 무엇으로 묶고, 무엇으로 반복하는가 |
| **③ 오류를 어떻게 처리하는가** | 오류를 언제 알려주고, 어떻게 복구하는가 |

## 1. 계보 한눈에

```
[기계 중심]
1972  C ─────────┐  빠르다. 대신 메모리 관리까지 전부 개발자 책임
                 │
[객체지향 등장]   ▼
1983  C++ ───────┐  코드 규모가 커지자 데이터와 로직을 클래스로 묶음(OOP)
                 │
[자동 메모리 관리·가상 머신] ▼
1995  Java ──────►  메모리는 언어가 관리, JVM 위에서 어디서나 실행
                    보완 언어: Kotlin(2011)
                    └─ 본교육: 백엔드 I·II, Spring Boot

[웹 계열]
1995  JavaScript ─► 브라우저에서 실행되는 유일한 언어
                    보완 언어: TypeScript(2012)
                    └─ 본교육: 프론트엔드, React

[동적 타입 계열]
1991  Python ─────► 가독성 우선 설계 → AI·데이터 분석의 표준

[선언형 — 별도 계열]
1974  SQL ────────► "어떻게"가 아니라 "무엇을"만 선언. 50년째 표준
                    └─ 본교육: DB 설계

[설정·인프라]
2001~ YAML / Dockerfile ─► 실행 환경·배포를 코드로 정의(IaC)
                    └─ 본교육: MSA·Docker·Kubernetes

[비교 기준]
1983  ABAP ───────► SAP 전용. 절차형 → ABAP Objects(OOP) → ABAP Cloud
                    업계 전체의 전환(절차형→OOP→클라우드)을 같은 순서로 거침
```

각 언어는 앞 언어의 한계를 해결하는 과정에서 나왔다. 그 한계가 무엇이었는지 알면 다음 언어의 문법이 규칙이 아니라 해결책으로 읽힌다.

## 2. 시대별 흐름 — 앞 언어의 한계와 다음 언어

### ① C (1972) — 빠르지만 전부 개발자 책임

운영체제(UNIX)를 만들기 위해 태어난 언어. 기계에 가까워서 지금도 속도가 필요한 곳(OS·임베디드)의 표준이다.

- **장점**: 빠르다. 하드웨어를 직접 다룬다. 이후 대부분 언어의 문법 조상(`if`, `for`, `{}`).
- **단점**: **메모리를 개발자가 직접 할당하고 해제**해야 한다. 해제를 잊으면 누수가 생기고, 잘못 접근하면 프로그램이 죽는다. 절차형(위에서 아래로)이라 프로그램이 커지면 구조화가 어렵다.

> **ABAP과 비교** — ABAP(1983)도 절차형으로 출발했다. REPORT 하나에 로직을 위에서 아래로 쓰고 PERFORM으로 분리하던 방식이 이 시대의 구조다. 다만 ABAP은 SAP 시스템 안에서 실행되므로 메모리 관리 문제는 직접 겪지 않았다.

### ② C++ (1983) — 객체지향의 등장

C로 짠 프로그램이 수십만 줄 규모가 되자 한계가 왔다. 데이터와 그 데이터를 고치는 함수가 흩어져 있어, 하나를 바꾸면 어디가 깨질지 추적이 어렵다. 이에 대한 답이 **객체지향(OOP)** — **데이터와 그 데이터를 다루는 함수를 "클래스"라는 한 단위로 묶는 방식**이다.

- **장점**: 큰 프로그램을 구조화할 수 있게 됐다. C의 속도는 유지.
- **단점**: C를 그대로 포함한 채 시작해서 복잡하다. 메모리도 여전히 수동 관리다.

> **ABAP과 비교** — 같은 전환을 ABAP도 거쳤다. 절차형 코드의 규모가 감당이 안 되자 클래스 기반의 **ABAP Objects**가 나왔다. "왜 클래스로 묶는가"의 답은 C→C++의 이유와 같다. 코드가 커지면 묶지 않고는 관리가 안 된다.

### ③ Java (1995) — 자동 메모리 관리, 어디서나 실행

C++의 두 가지 문제(수동 메모리, 플랫폼 종속)를 해결하기 위해 나왔다. 메모리는 **가비지 컬렉션**이 자동으로 회수하고, 코드는 **JVM**(자바 가상 머신) 위에서 실행돼 운영체제와 무관하게 같은 코드가 돈다("Write Once, Run Anywhere"). 처음부터 객체지향으로 설계됐다.

- **장점**: 안정적이고, 강한 타입이라 실수를 컴파일 시점에 잡는다. Spring 생태계와 함께 **대기업 백엔드 SI 점유율 1위**. 컬렉션(ArrayList·HashMap)과 Stream으로 대량 데이터를 구조적으로 처리한다.
- **단점**: 같은 일에 코드가 길다. 이를 보완한 언어가 Kotlin(2011) — JVM 위에서 돌면서 문법을 간결하게 줄였다.

> **ABAP과 비교** — Java의 "타입 선언 필수, 틀리면 컴파일 오류"는 ABAP의 `DATA` 선언과 같은 방식이다. 실행 전에 오류를 잡는 세계. SAP도 ECC에서 Cloud로 가며 OOP 기반으로 재편됐는데, Java의 구조는 그 방향과 같다.

### ④ JavaScript (1995) — Java와 다른 계열

Java와 이름만 비슷할 뿐 다른 계열이다. 웹페이지를 움직이게 하기 위해 **브라우저 안에서 실행되는 언어**로 태어났다. 타입 선언 없이 바로 쓰는 **동적 타입**이라, 오류는 실행 시점에야 드러난다.

- **장점**: 브라우저에서 실행되는 유일한 언어. Node.js(2009) 이후 서버까지 확장돼, **하나의 언어로 프론트엔드(React)·백엔드·모바일 개발이 가능**하다. 세계 사용률 1위.
- **단점**: 동적 타입이라 큰 프로젝트에서 런타임 오류가 잦다. 이를 보완한 언어가 **TypeScript**(2012) — JavaScript에 타입 선언을 다시 추가했다. 유연성을 위해 타입을 뺐다가, 규모가 커지자 다시 넣은 것이다.
- **핵심 특징**: **비동기 처리**(Promise·async/await). 서버에 요청을 보내놓고 응답을 기다리는 동안 화면이 멈추지 않게 한다. 사전학습에서 쓴 axios·await가 이것이다.

> **ABAP과 비교** — 특강 메모에 "Java는 비동기로 데이터 처리"라고 적었다가 정리 과정에서 정정했다. **비동기가 핵심인 쪽은 JavaScript**고, Java의 특징은 컬렉션·Stream이다. 동적 타입의 "실행해야 오류를 안다"는 방식은 ABAP의 컴파일 체크에 익숙한 입장에서는 낯선 부분이라, React 학습 시 유의할 지점이다.

### ⑤ Python (1991) — 가독성 우선

본교육 과목은 아니지만 계보 이해를 위해 포함했다. 문법이 영어 문장에 가깝고, 들여쓰기 자체가 문법이다.

- **장점**: 배우기 쉽다. 라이브러리 생태계 덕에 **AI·데이터 분석의 표준**이 됐다.
- **단점**: 실행 속도가 느리다. 동적 타입의 약점(런타임 오류)은 JavaScript와 공유한다.
- **포함 이유**: AI 활용이 이 캠프의 목적인 이상, AI 도구 대부분이 Python 기반이라는 사실은 계속 마주치게 된다.

### ⑥ SQL (1974) — 선언형, "어떻게"가 아니라 "무엇을"

위 언어들과 다른 종류다. 절차를 적는 게 아니라 **원하는 결과만 선언**한다(선언형). `SELECT 이름 FROM 사원 WHERE 부서 = '영업'` — 어떻게 찾을지는 데이터베이스가 결정한다.

- **장점**: 50년째 표준. 모든 서비스에 데이터베이스가 있는 한 수요가 유지된다. 트랜잭션·ROLLBACK으로 데이터 무결성을 보장한다.
- **단점**: 복잡한 절차 로직에는 부적합해서 항상 다른 언어와 짝으로 쓰인다. JPA(Java에서 DB를 객체처럼 다루는 도구)를 배우기 전에 선행해야 하는 이유이기도 하다.

> **ABAP과 비교** — 네 언어 중 가장 익숙한 영역이다. ABAP 작업의 상당 부분이 `SELECT`로 테이블을 다루는 일이었다. "무엇을"만 선언하면 시스템이 가져오는 방식, 테이블·JOIN·집계 모두 이미 써봤다. 본교육 SQL은 복습에 가까울 것으로 예상한다.

### ⑦ YAML / Dockerfile (2000년대~) — 설정과 인프라를 코드로

실행 로직이 아니라 **환경과 설정을 코드로 정의**하는 도구다. "이 앱은 이런 환경에서 이렇게 실행돼야 한다"를 파일로 선언하면(Dockerfile), 어디서든 같은 환경이 재현된다. Kubernetes는 그 선언(YAML)을 읽고 다수의 서버를 자동으로 관리한다 — **코드로 인프라를 관리한다(IaC)**.

- **장점**: 클라우드 시대의 공통 형식. AWS·Azure·GCP 배포, DevOps·MLOps가 이 위에 있다. 오류 처리 관점도 다르다 — 사람이 고치는 게 아니라 시스템이 **자동 복구**한다(오토스케일·헬스체크).
- **단점**: YAML은 들여쓰기 하나에 전체가 깨질 만큼 문법이 엄격하다(탭 금지, 스페이스만).

> **ABAP과 비교** — 네 영역 중 가장 낯설다. SAP 환경에서는 인프라를 베이시스(Basis)팀이 담당해서, 환경을 코드로 정의한다는 방식 자체를 접한 적이 없다. 예습이 가장 필요한 영역이다.

## 3. 본교육 4언어 비교 — 3질문 기준

| | **Java** | **JavaScript** | **SQL** | **YAML/Dockerfile** |
|---|---|---|---|---|
| 본교육 과목 | 백엔드·Spring Boot | 프론트엔드·React | DB 설계 | MSA·Docker·K8s |
| ① 저장 | 강한 타입 — 선언 필수, 컴파일이 검사 | 동적 타입 — 런타임에 결정 | 테이블 | Key-Value 설정 |
| ② 처리 | 컬렉션·Stream (대량 데이터 구조화) | **비동기**(Promise·async/await)·배열 메서드 | 선언형 — JOIN·집계 | 선언 → 시스템이 실행 |
| ③ 오류 | try-catch, 컴파일 시점 차단 | try-catch·`.catch()`, 실행 후 발견 | 트랜잭션·ROLLBACK | 자동 복구(헬스체크·오토스케일) |
| 배우는 이유 | 대기업 백엔드 표준 | 풀스택 가능한 유일 언어 | 모든 서비스의 토대 | 클라우드 시대 필수 |
| ABAP과의 거리 | 가깝다 (강한 타입·OOP) | 멀다 (동적 타입·비동기) | 가장 가깝다 | 가장 멀다 |

## 4. 종합 — ABAP의 위치와 시작점 정리

ABAP은 SAP 시스템 전용의 도메인 특화 언어라 계보의 본류는 아니다. 다만 업계가 거친 전환(절차형 → OOP → 클라우드)을 ABAP도 같은 순서로 거쳤다 — 절차형 ABAP → ABAP Objects → ABAP Cloud. 계보의 주요 전환점마다 대응되는 ABAP 경험이 있는 이유다.

| 이미 익숙한 것 | ABAP에서의 근거 | 연결되는 과목 |
|------|------|------|
| 강한 타입 (선언하고 시작, 실행 전 검사) | `DATA` 선언 | Java |
| 테이블 단위 데이터 처리 (행 반복·가공) | 내부 테이블·`LOOP AT` | Java 컬렉션·Stream, JS 배열 메서드 |
| SQL | Open SQL `SELECT` | SQL·JPA |
| 절차형→OOP 전환의 이유 | ABAP Objects, ECC→Cloud | Java 설계 구조 |
| 새로 배워야 하는 것: 동적 타입·비동기 | — | JavaScript·React |
| 새로 배워야 하는 것: 인프라의 코드화 | — | Docker·K8s |

🚧 추후 보완: SAP이 ECC→Cloud 전환에서 OOP 기반을 택한 이유를 공식 문서로 확인해 채운다. Java가 처음부터 OOP로 설계된 이유와 같은 질문이다.
